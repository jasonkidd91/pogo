# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Pokémon GO information site plus the domain context needed to keep it accurate. Three parts
that serve different purposes — know which one you're in:

| Directory | Purpose |
|---|---|
| `web/` | The site. Static HTML/CSS/JS, no build step. Two runtime dependencies: the Firebase SDK loaded from the CDN by `auth.js`, and the ScrapedDuck event feed fetched by `events.js`. |
| `scripts/` | Python generators that produce the site's data files from Bulbapedia. |
| `pokemon-go/` | Portable domain-knowledge **skill** — game mechanics, formulas, source hierarchy. Not part of the site. Copy into other projects. |
| `docs/` | Three CLAUDE.md files generated by different models, plus `MODEL-COMPARISON.md` analysing them. Historical/reference only. |

## Commands

```bash
# Serve the site. Do NOT open a page over file:// — the origin is opaque, so Google sign-in
# and Firestore both fail. localhost is an authorised Firebase domain by default; any other
# host has to be added under Authentication → Settings → Authorized domains.
python3 -m http.server 8777 --directory web

# Regenerate data from Bulbapedia — see "Generated files" below
python3 scripts/update_megas.py
python3 scripts/update_dynamax.py

# Refresh the events-page FALLBACK snapshot. The page fetches the feed live on every load;
# this is only what it shows if that fails, so this is not how the page stays current.
python3 scripts/update_events.py

# Syntax-check JS (no test suite exists)
node --check web/app.js

# Deploy the Firestore security rules — without these the tracker's data is unprotected
firebase deploy --only firestore:rules
```

There is no linter, test runner, or package manager. Verification is done by loading pages in
a browser and asserting against the DOM (Playwright MCP is available).

## The rule that governs this codebase

**Pokémon GO is live-service software. Most of what players ask about rotates.** Answering or
coding rotating content from memory is the dominant failure mode here — it produces confident,
plausible, wrong output.

Before writing any game fact into code, classify it:

- **STABLE** (formulas, type chart, CPM) — safe from `pokemon-go/references/stable-mechanics.md`.
- **SLOW** (rosters, feature rules, energy costs) — belongs in a generated data file with a
  source URL and date in its header.
- **LIVE** (current events, raid rotations, Max Battle tiers, egg pools) — **must be looked up**,
  and generally should *not* be baked into a static file at all. The events page is the worked
  example: it fetches the feed at runtime and treats its baked copy as a labelled fallback.

Read `pokemon-go/SKILL.md` before answering gameplay questions.
`pokemon-go/references/contested-facts.md` lists facts where sources disagree — check it before
asserting anything about 2025–26 mechanics.

### Never trust an LLM-summarised fetch of a large table

This has concretely failed in this repo: a fetch truncated to the first row of each section of
a table, and another reported a Pokémon as unreleased that had shipped the day before. For
anything table-shaped, fetch raw wikitext and parse deterministically — that's what
`scripts/bulbapedia.py` exists for.

## Generated files — do not hand-edit

`web/mega-data.js` and `web/max-data.js` carry a `GENERATED` header. Edits are lost on the next
refresh. Change the generator instead.

`scripts/bulbapedia.py` documents two traps that silently corrupt these lists. Both have bitten:

1. **Unreleased entries are HTML-commented** inside the wikitable. Parsing without stripping
   comments pulled in ~32 datamined Megas that aren't in the game.
2. **Cells carry attributes** — `| data-sort-value="100" | 100<ref…>`. Reading the cell naively
   yields no number, which then inherits the previous row's value via the rowspan fallback.
   This once made Mega Slowbro read 300 energy instead of 100.

Both generators verify every sprite URL and raise rather than write bad data. Keep that.

`web/data.js` (the Mega Finale event) is hand-written but carries its verification sources and
date in the header — preserve that convention for new event data.

## Site architecture

Plain scripts, no modules or bundler. **Load order matters**: `store.js` → `auth.js` →
data file → page script.

- **`store.js` is the single source of truth for identity.** Every page writes to one Firestore
  document using canonical, name-derived IDs, which is what makes checkmarks shared
  across pages:

  ```
  mega:mega-beedrill    Megas and Primals (event pages and megas.html share these)
  dmax:bulbasaur        Dynamax-capable
  gmax:venusaur         Gigantamax — deliberately separate from the Dynamax entry
  ```

  A page-local or day-scoped key breaks cross-page sync and is a bug. Progress is long-lived:
  only an explicit Reset clears it, and only its own prefixes. It also holds the shared nav —
  register new pages in `buildNav()`.

- **`auth.js` — Google sign-in and the Firestore backend.** It imports the Firebase modular SDK
  with dynamic `import()` from a classic script, so the site stays module-free and build-free.
  Load order is `store.js` → `auth.js` → data → page script.

  **Signing in is optional; tracking is not.** Signed out the lists render fine but nothing can
  be ticked — `Store.toggle` refuses, `Store.locked` is true, and a gate banner offers sign-in.
  There is deliberately no browser-local fallback set: it would diverge from the account and
  then need reconciling. Cards must call `trackerToggle(key)`, not `Store.toggle(key)` — that
  wrapper is what turns a refused tick into a sign-in prompt.

  Progress written before sign-in existed (the old `pogo.caught.v1` localStorage key) is
  adopted once, on the first server snapshot for a brand-new account, then dropped.

- **`collection.js`** — card renderer, search and filters shared by `megas.html` and
  `dynamax.html`. Those two pages hold their own render logic inline.
- **`app.js`** — Mega Finale tracker rendering only (habitat grouping, live-window detection).
- **`events.js`** — the front page. See "The events page is live data" below.

- **Only `<body data-tracker>` pages get the sign-in gate.** `auth.js` returns early without it.
  The events page has nothing to tick, so it has no gate; a tracker page that forgets the
  attribute renders inert cards with nothing explaining why.

### The events page is live data

`index.html` is a summary of what is on now and next, not a tracker. It fetches
`ScrapedDuck`'s JSON of the LeekDuck event list on **every page load** and renders that;
`web/events-data.js` is a generated fallback shown only while that request is in flight or if
it fails, and the footer states which of the two is on screen. Regenerating the snapshot is
not how the page stays current — that is the whole design, because events rotate daily.

Three things there are easy to get wrong:

- **A stamp without a trailing `Z` is local wall-clock time.** A Community Day at 14:00 starts
  at 14:00 wherever the player is. **With** a `Z` it is one worldwide instant, which is how GO
  Battle League rotations are published, and it lands at a different clock time per zone.
  `new Date()` reads both correctly; the suffix only decides whether the card is tagged
  `global`. Do not normalise it away in the generator or the renderer.
- **The snapshot paints before the fetch resolves.** Same lesson as the sign-in gate: a page
  that waits for the network shows nothing and reads as broken.
- **Trackers are opt-in.** An event appearing in the feed is not a reason to build a catch
  list for it. `TRACKERS` in `events.js` maps the few feed ids that have one; build a new one
  only when asked.

### Free tier is the budget

The Firebase project is on Spark: 50k Firestore reads, 20k writes, 20k deletes a day. The design
of `auth.js` follows from that and should not be "simplified" away:

- **One document per user** — `users/{uid}.caught` is an array of keys. Loading a whole
  collection log costs 1 read, not 1 per Pokémon. Never split it into a subcollection.
- **Writes are debounced ~1.5s and rewrite the whole array** — ticking forty boxes is one write.
  The trade is last-writer-wins between two devices inside the same window; that is acceptable
  for a personal catch list and the live listener keeps the window small.
- **One `onSnapshot` per page**, on one document. Multi-tab persistence elects a single tab to
  own the connection.
- **Analytics is deliberately not wired up** even though `measurementId` is in the config — it
  is ~50 kB per page and measures nothing this site acts on.

`firestore.rules` in the repo root is what actually protects the data — the web API key in
`auth.js` is a public project identifier and authorises nothing. Deploy the rules.

### Conventions that look like bugs but aren't

- **Sprites come from `img.pokemondb.net/sprites/home/normal/<slug>.png`**, keyed by name. Megas
  are `<species>-mega` / `<species>-mega-x`, Primals `<species>-primal`, Gigantamax
  `<species>-gigantamax` (not `-gmax`). Entries with `artFallback` swap to base-species art on
  error — 13 GO-original Megas have no mainline artwork and are tagged `GO ORIGINAL`.
- **Event time windows are local time.** `isoDate` is compared against local date parts on
  purpose; `toISOString()` gives the UTC date and mis-fires across midnight.
- **Primal Kyogre/Groudon and Mega Rayquaza show a weather pill.** Bulbapedia's "Boosted types"
  column is weather-based for those three and is not their own typing; the generator keeps both.
- **The sign-in gate is drawn before Firebase finishes loading**, in a muted "Checking your
  sign-in…" state, and is never hidden. Hiding it while the SDK downloads looks tidier on a
  fast connection and is much worse on a slow one: the cards render inert with nothing saying
  why. Measured on throttled 3G, `dynamax.html` sat unexplained and dead for **15.6 s**; drawing
  the gate immediately cut that to 13 ms. Don't reintroduce a `display: none` while loading.
- **The sticky summary collapses on phones once you scroll.** At full height it is ~335px —
  40% of a 390x844 viewport, 50% of a small phone — pinned above a list of up to 160 cards.
  Under 560px, `body.scrolled` shrinks it to a ~50px strip (two stats, a hairline bar, a
  `Filters` affordance); tapping the strip or focusing anything inside it re-expands, and
  scrolling back to the top restores it. `stickySummary()` in `store.js` only toggles the
  class — all the sizing is CSS, so desktop is untouched.

- **Species raid class is shown; the current rotation tier is not.** These are two different
  things and the distinction is the whole point. A species' battle *class* is stable and
  generated into the data files — `raid`/`stars`, rendered as the pill on each card: Mega Raid
  (★4), Primal Raid (★5), Legendary Mega Raid (★6, Legendary and Mythical Megas) and
  Gigantamax Battle (★6). It is derived from the rule quoted on `Raid_Battle_(GO)` plus
  Bulbapedia's Legendary/Mythical **categories** — never from memory, and never by scraping
  the Legendary article, which names Ditto and Bulbasaur in prose (see trap 3 in
  `scripts/bulbapedia.py`).

  What stays absent: **which** Pokémon is in the raid or Power Spot rotation today, the
  per-encounter Max Battle tier of a plain Dynamax Pokémon, and Dynamax types. Those rotate
  weekly and would be stale within days. **Super Mega Raid is also deliberately not derived**
  — Bulbapedia describes it as an event-driven shielded variant of a Mega Raid, not a property
  of the species, so a per-species value would be confidently wrong. The event page's
  hand-written `tier: 'Super Mega Raid'` is verified for that one event and stays hand-written.

## Project skills

`.claude/skills/` holds:

| Skill | For |
|---|---|
| `update-events` | The front page — refreshing or fixing the What's on list |
| `update-megas` / `update-dynamax` | Regenerating the two collection data files from Bulbapedia |
| `new-event-tracker` | Building a catch-list page for an event **when asked** |
| `verify-site` | Browser verification, including getting Chromium up without root |
| `deploy-site` | Shipping to GitHub Pages and confirming it is actually live |

Prefer them over improvising — they encode the verification steps and the failure modes above.

Per the user's global convention, mirror any change to files under `.claude/` into
`~/Documents/claude backup/pogo/` before editing.
